# v1.8.33（紧急修复）：每滚一下，整台电脑的鼠标卡一秒

## 事故

你反馈的"严重影响电脑使用"是真的，而且是我上一版引入的。日志实锤：

`
13:57:55 [INFO] 原生平滑：deepseek harness.exe（Chrome_WidgetWin_1）倍率 5.00× → 单个事件 -1800 单位
13:58:00 [WARN] 钩子回调耗时偏高：最大 1006.4 ms / 4 次
13:58:10 [WARN] 钩子回调耗时偏高：最大 1013.5 ms / 13 次
13:58:15 [WARN] 钩子回调耗时偏高：最大 1002.7 ms / 11 次
`

**钩子回调每次卡 1000 毫秒** —— 低层鼠标钩子是全局串行的，一个回调卡住，
整台机器的鼠标/滚轮就跟着卡。这就是你感觉到的"电脑不能用了"。

## 根因

v1.8.32 为了让 Electron/Chromium 用自己的平滑，我在**钩子回调里直接调用了 SendInput**：

- 低层钩子是全局的，注入的事件要再进一次我们自己的钩子；
- 而当前回调还没返回 → Windows 只能等钩子超时（实测 ~1000ms）才继续。

同一类错误其实一直存在于**细腻模式的转发**里（ForwardRaw / ForwardWhole），
所以你之前"有时候不能顺利使用"也是它。

## 修法

**钩子线程只入队，绝不注入。**

- 新增 ScrollAnimator.PushPassthrough：钩子线程把"原样要发的事件"排进无锁队列；
- 动画线程（不在钩子回调栈里）负责真正 SendInput —— 立即返回，延迟最多一帧（约 6ms）；
- 细腻模式的两种转发、Electron 的原生平滑转发，全部改走队列。

## 硬护栏（防止再犯）

- InputInjector.InHookCallback：以线程静态标记"现在是钩子回调栈"，
  在钩子线程里调 SendWheel 会被**直接拦下并记错误日志**，不再让整机陪着卡；
- 看门狗升级：回调一旦超过 **250ms**，主动把钩子摘掉再装上 —— 摘掉的那一瞬间系统输入就恢复。

## 实测（同一台机器、同一套注入）

| | 修复前 | **修复后** |
|---|---:|---:|
| 钩子回调最大耗时 | **1006 ms** | **4.47 ms**（173 次采样） |

--selftest **367 项**（新增：钩子回调里注入会被拦下）。
