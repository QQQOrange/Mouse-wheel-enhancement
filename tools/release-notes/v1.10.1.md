# v1.10.1：细腻模式的守护进程瘦了 19 倍

## 这一版里还有 v1.10.0 的内容

v1.10.0 没有单独发过 release，所以从 v1.9.9 升上来的用户一次拿到两版的东西：

- **脉冲缓动（Pulse）**——照着 SmoothScroll 的曲线重建：起步快、尾巴收得干净，默认 160 ms（SmoothScroll 自己默认 360 ms，那个时长偏飘）。设置里多一个「强度」滑条（2–8，实测 4.0 最像原生）。
- **帧同步发帧**——每个显示器刷新周期发一次 SendInput（DwmFlush 对齐）；拿不到 vblank 或连错 3 次就永久退回定时器，不会卡死。
- 新装用户默认就是「脉冲 + 160 ms」，老配置一个字段都没改。

## 怎么来的

量开销的时候翻出来一个数：细腻模式退出后要把系统的「每次滚动几行」写回去，
做法是**把整个程序再启动一份**（`--fineguard`）去等主进程退出。那 48 MB 里
WPF 的页面、资源字典、主题模板全被解析了一遍 —— 只为了等一个进程结束、
写一个注册表值。

## 数字（同机实测）

| 指标 | 上一版守护进程 | 这一版 |
| --- | --- | --- |
| 工作集 | 47.7 MB | **2.52 MB** |
| 私有字节 | 11.9 MB | **6.75 MB** |
| 线程 | 5 | 11（CLR 后台线程，CPU 0.05 s） |
| 加载模块 | 全部 WPF | 39 个 |

工作集降了约 **19 倍**。守护进程只在主程序退出那段时间活着，所以这 2.5 MB
平时根本见不到 —— 但用户开着细腻模式一整天，退出时不该需要 48 MB 来收尾。

## 怎么做到的

.NET 10 的 WPF 生成器不再理会 `DISABLE_XAML_GENERATED_MAIN`（生成的
`App.g.cs` 第 94 行是裸的 `public static void Main()`，加自定义 `Main` 直接
`CS0017: 程序定义了多个入口点`）。所以换成 `[ModuleInitializer]`：CLR 在调用
入口方法**之前**就跑它，而我们判断出是 `--fineguard` 就干完活
`Environment.Exit(0)`，WPF 一行都没启动。

`PresentationFramework.dll` 还是会被加载 —— 入口 `Main` 声明在 `App` 上，
`App : Application`，JIT 解析入口签名必须把基类带进来。这是进程内的下限，
但页面、样式、资源字典一个都没解析，所以是 2.5 MB 而不是 48 MB。

## 手感完全没变

细腻模式的开关、补偿倍数（注入量 ×3）、备份文件、`pid + 启动时间` 认主、
退出还原、崩溃后下次启动的 RunOnce 恢复 —— 一个字节都没动。升级不需要改配置。

## 验证

- 自检 **525 项全过**（新增守护进程参数解析 7 项：三参数、第 4 参数 ticks、
  大小写、参数不全、非数字、普通启动不算、不存在的 pid）。
- 单文件发布后实测：守护进程工作集 2.52 MB / 私有 6.75 MB / 11 线程；
  主进程结束后守护进程自行以退出码 0 结束，系统行数写回，备份文件删除。
- 装机后走真实链路（启动器 → 释放 1.10.1 主程序 → 细腻模式生效）：系统行数
  1、备份 `3 / pid / ticks`、守护进程 3.57 MB。

## 一个坑，写在这里给以后的自己

模块初始化器抛异常不是「这条路径失败」，而是**整个进程起不来** —— 用户看到的
是「双击没反应」，连日志都没有。所以 `Core/FineGuard.cs` 里所有路径都包在
`try/catch` 里，出错只写一条 warn，然后继续正常启动。
