# v1.8.24：整格模式的一个藏了三版的 bug，以及它换来的"更好的平滑"

## 1. WholeNotch 是个死开关（真 bug）

从 v1.8.3 起动画器就有"整格模式：一帧只发一个整档"的开关，**但循环里从来没读过它**。
于是 WPF / WinForms / Qt 这些"只认事件个数、不看 delta 大小"的框架会收到：

> 3 档 → 引擎算出 3 档 → 动画器按曲线摊成几十个亚格 delta → 应用数出几十档

也就是说在那些程序里，加速 3 倍可能滚出 30 多档。以前只有整格语义的**纯函数**被测过，
动画器这一层没有测试，所以一直没暴露。

## 2. 现在的整格调度

三个条件同时满足才发一档：还剩至少一档、曲线"欠"够了一档、距上一档 ≥ 12ms。

第三条是节奏下限；第二条顺带把尾段做顺了 —— 余量越少，攒够一档越慢，**最后一档自然被拉开到
30~60ms 之后**，而不是匀速 12ms 发完再硬停。

实测（--featurecheck 新增真跑动画线程的一组）：3 档 → **正好 3 帧**、每帧都是 120 的倍数、
总量 **360 一单位不差**、两档间隔 **≥ 8ms**。

## 3. 整格框架的"亚格"边界（说清楚）

这类框架的最小粒度是"一个事件 = 系统行数 × 行高"（默认 3 行 = 60px）。想更细只有一条路：
**细腻模式**（v1.8.17）把系统行数降到 1 —— 每档变 20px，粒度细 3 倍，再配合新的减速调度，
这已经是该语义下的极限。真正的亚像素插值必须由应用自己参与动画（Chromium 就是自己做的），
输入层伪造不出来。
